# Последние технические уточнения к плану v2.2 — без изменения согласованных этапов

**Вердикт:** направление `staging → validation → atomic apply`, этапы 0–6 и базовая бизнес-семантика принимаются. **Не переписывай весь план заново.** Включи перечисленные ниже пункты в технический дизайн этапа 0 и закрой их проверяемыми алгоритмами/тестами **до начала реализации этапа 1**. На этом шаге код не изменяй.

## 1. `ownerToken` должен обозначать попытку владения, а не только импорт

В плане написано «ownerToken (UUID importId)». Для восстановления `PREPARED` это опасно: старый worker и новый recovery-worker **одного `fileUploadId`** могут получить одинаковый token, и прежний worker сможет пройти fencing после восстановления lease новым worker.

- Раздели `fileUploadId/importId` (неизменная идентичность загружаемого файла) и `ownerToken` (новый случайный UUID **при каждом новом приобретении/перехвате права**). Дополнительно рассмотри монотонный `fencing_generation` в строке блокировки/метаданных импорта.
- При recovery `PREPARED` явно опиши атомарное переприсвоение владельца/lease, проверку `fileUploadId`, передачу нового token воркеру и условие отклонения всех действий прежнего owner.
- Проверка права должна производиться при переводе `PREPARED → APPLIED` **внутри той же транзакции**, где выполняются бизнес-изменения и `file_upload.SUCCESS`.
- Тест: старый worker не умер, lease истёк, новый worker перехватил **тот же** `fileUploadId` и успешно применил импорт; старый worker не может повторно записать бизнес-данные, изменить статус или освободить новую блокировку.

## 2. Не использовать `now()` как текущие часы в длинном PostgreSQL apply

В PostgreSQL `now()` / `CURRENT_TIMESTAMP` фиксируется **на момент начала транзакции**. Условие `lease_expires_at > now()` в конце длительного apply может ошибочно считаться истинным после реального истечения lease.

- Для проверки реального срока истечения в конце apply используй `clock_timestamp()` (или другое доказанно эквивалентное решение) **вместе с проверкой `ownerToken` и поколения владения**.
- Финальный условный `UPDATE` строки права должен выполняться в apply-транзакции **непосредственно перед завершением/commit**, с проверкой числа изменённых строк. Полученная row-level блокировка должна не позволять другой транзакции сменить owner между fencing-проверкой и commit.
- Учитывай, что heartbeat/перехват права и финальный fencing могут блокировать друг друга по строке `upload_permission`: опиши последовательность захвата блокировок, минимальную критическую секцию, `lock_timeout`, поведение при ожидании и то, как избежать взаимной блокировки.
- Не выполняй необязательных длительных операций между последней fencing-проверкой и commit. В идеале успех/phase/SUCCESS и финальную проверку связывает одна транзакция без вложенных `REQUIRES_NEW`.
- Тест: apply длится дольше TTL; при `now()` тест не должен ложно проходить, при корректной проверке устаревший владелец откатывается. Добавь сценарии с одновременным heartbeat, перехватом и коротким TTL.

## 3. Подробно согласовать судьбу `PREPARED` при истекшем lease и новом POST

Объявления «поллер восстанавливает PREPARED» недостаточно: право может быть `upload_allowed=false` с мёртвым владельцем, либо новым POST может быть захвачен глобальный слот после TTL.

- Опиши процедуру атомарного **reclaim** истёкшего слота под восстановление `PREPARED`: какое условие SQL CAS, какой `fileUploadId`, как назначаются `ownerToken`, `lease_expires_at`, `fencing_generation`; какое состояние прежнего owner проверяется.
- Укажи правило порядка: **подхват незавершённого PREPARED имеет приоритет над новым POST** либо PREPARED отклоняется как устаревший. Это бизнес-решение нельзя оставлять случайному race between poller and HTTP. Сохранить отказ 403 при реально активном импорте.
- Поллер не должен переводить живой, но медленный `PREPARING` в `ERROR` только из-за временной GC-паузы без описанного механизма lease/проверки живости. Потерявший право worker обязан прекратить запись staging/переход PREPARED.
- Тесты: рестарт на PREPARED, heartbeat прекратился; restore при занятом/истёкшем global lock; новый POST одновременно с recovery; pause JVM длиннее TTL.

## 4. Конфликты Jira/PULT: определить *базу сравнения* и закрыть phantoms

План требует сравнить «`agent.updated` из staging-момента подготовки» с текущим значением, но staging заявлен преимущественно хранилищем исходных Excel-значений/бизнес-ключей. Нужно определить, **где и когда** достоверно записывается исходная версия/состояние.

- Либо сохраняй baseline-версию/контрольные значения, считанные из БД в согласованной точке подготовки, и проверяй их при apply, либо проводи полное чтение актуального состояния и построение diff **после необходимых блокировок внутри apply**. Выбранный алгоритм должен быть явно зафиксирован; не считать наличие поля `updated` достаточным для всех дочерних таблиц.
- Приведи карту *реальных* изменяющих путей Excel/Jira/PULT/шедулеров/ручек на уровне основных и дочерних таблиц. Для каждой записи укажи механизм конфликта. `FOR UPDATE` строки агента не защищает от конкурентных INSERT новой дочерней строки и «отсутствующих» записей; при `READ COMMITTED` возможны phantom changes. Если используешь `SERIALIZABLE`, опиши круг участвующих транзакций и retry при `40001`, не утверждай, что это универсальное решение без доработки других writers.
- Проверь `disableDeletedAgents`, глобальную очистку контактов, справочники и процессы, которые изменяются массово и могут конфликтовать с внешними writers.
- Тест: во время подготовки Jira/ручка меняет (а) агента, (б) дочернюю сущность без `agent.updated`, (в) добавляет связь, ранее отсутствовавшую; итог — отсутствие тихой потери данных или подтверждённая политика конфликтов.

## 5. Различать «занято» и «БД недоступна»

Fail-closed — верно, но `isUploadAllowed() = false` при SQL-ошибке может превратить отказ БД в `403 file.upload.is.not.allowed`, который означает **активный импорт**.

- Сохрани `403` для реально занятой блокировки; при недоступности БД или ошибке CAS верни контролируемую техническую ошибку (`503`/`500` согласно принятому контракту и обработчику исключений) с логированием первопричины. Не создавать запись `GLOBAL` из широкого `catch Exception`.
- Миграция гарантирует строку `GLOBAL` (`INSERT ... ON CONFLICT DO NOTHING` в транзакции миграции), а сервис обрабатывает отсутствующую запись явно, не как «разрешить импорт».
- Тесты: занят слот; отсутствует строка; БД недоступна; два параллельных CAS; освобождение старым owner после захвата новым.
