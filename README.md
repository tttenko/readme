# Задача: написать unit-тесты и mock-тесты для связанных AI-объектов и отклонений инициатив

## Общие требования

Используй существующий стек проекта:

- Kotlin
- JUnit 5
- MockK
- Spring Boot
- AssertJ или существующие в проекте assertions

Перед написанием тестов изучи реальную реализацию контроллеров, сервисов, DTO, репозиториев, конфигурации отклонений и существующие тесты проекта.

Не изменяй production-код без необходимости. Не создавай интеграционные тесты, не поднимай PostgreSQL, Redis и Spring-контекст для обычных unit-тестов.

Тестируй бизнес-поведение, а не приватные методы и внутренние детали реализации. Зависимости изолируй через MockK. Используй `verify`, когда необходимо проверить отсутствие лишних вызовов или взаимодействие с внешними сервисами.

**Приоритет P0 — обязательные тесты. P1 — дополнительные полезные проверки.**

## 1. GET /api/v1/ai-agent/{initiativeId}/meta-ai-objects

Основные классы: `MetaAiObjectsService`, `MetaAiObjectDeviationCalculator`, `MetaAiObjectsController`.

### P0 — обязательные тесты

1. **Получение нескольких активных объектов**

   Для существующей инициативы с CROSSGOAL вернуть несколько активных записей. Проверить правильность `id`, `ci`, `name`, `type`, `gigaUsageId`, `metaLink`.

2. **Преобразование типа объекта**

   Проверить три сценария:
   - `isAgent = true` → `AGENT`;
   - `isAgent = false` → `LLM_SOLUTION`;
   - `isAgent = null` → `null`.

   Обязательно проверить, что `false` не интерпретируется как отсутствие типа.

3. **Объект без дополнительных сведений**

   При `name = null`, `isAgent = null`, `gigausage = null`, `metaLink = null` объект должен присутствовать в ответе. Проверить формирование двух отклонений.

4. **Отклонение AI_OBJECT_NAME_NOT_FILLED**

   Проверить срабатывание правила при `name = null`, пустой строке и строке из пробелов. При заполненном имени отклонения быть не должно.

5. **Отклонение AI_OBJECT_TYPE_NOT_FILLED**

   Правило срабатывает только при `isAgent = null`. Для `true` и `false` не срабатывает.

6. **Отключение правил конфигурацией**

   Проверить:
   - `meta-ai-objects.deviations.enabled = false` → отклонений нет;
   - конкретное правило `enabled = false` → оно не возвращается;
   - все правила выключены → `deviationCount = 0`.

7. **Приоритеты и тексты отклонений**

   Отклонения сортируются по `priority`. Поля `title`, `description`, `priority` берутся из конфигурации, а не захардкожены. При одинаковом приоритете проверять стабильный порядок по коду, если он предусмотрен реализацией.

8. **Корректность deviationCount**

   Проверить, что `deviationCount` всегда равен количеству элементов в `deviations`: 0, 1 или 2.

9. **Отсутствие активных объектов**

   Для существующей инициативы без активных объектов вернуть `objects = []`, без исключения.

10. **Корректная изоляция объектов инициативы**

    Один CROSSGOAL может принадлежать нескольким инициативам. Проверить, что запрос для `initiativeId = A` не возвращает объекты инициативы `B`. Проверить передачу и `initiativeId`, и CROSSGOAL в метод репозитория.

11. **Проверка инициативы**

    - Некорректный `initiativeId` → 400.
    - Несуществующая инициатива → 404.
    - Отключённая инициатива → результат согласно действующей реализации проверки доступности.

### P1 — дополнительные тесты

12. При отсутствии CROSSGOAL возвращается пустой список, если это соответствует текущей реализации.

13. Неактивные объекты (`isActive = false`) не должны попадать в результат. Проверить контракт вызова репозитория; сам SQL-фильтр нельзя доказать unit-тестом с моками.

14. Отсутствие объектных отклонений у полностью заполненного объекта.

## 2. GET /api/v1/ai-agent/{initiativeId}/meta-ai-objects/history

Основные классы: `MetaAiObjectsHistoryService`, `MetaAiObjectsController`, `InitiativeAiObjectHistoryRepository`, `UserAccountService`.

### P0 — обязательные тесты

15. **Успешное получение истории**

    Репозиторий возвращает несколько событий `FILE_IMPORT`. Проверить маппинг `id`, `eventAt`, `eventType`, `changedObjectsCount`, `message`, `editor`.

16. **Сортировка событий**

    Проверить формирование `PageRequest` с сортировкой:
    - `createdAt DESC`;
    - `id DESC`.

    Использовать `slot<Pageable>()` либо `match`, чтобы проверить параметры репозитория.

17. **Пагинация**

    Проверить передачу `page`, `size` и сохранение метаданных `Page`: `totalElements`, `totalPages`, `number`, `size`.

18. **Пустая история**

    Если история инициативы отсутствует, вернуть страницу с `content = []`, без ошибки. Убедиться, что получение пользователей из `prm-auth` не приводит к внешнему запросу при отсутствии идентификаторов.

19. **Получение ФИО редакторов**

    Если история содержит события нескольких пользователей, проверить:
    - сбор уникальных `createdBy`;
    - один пакетный вызов `UserAccountService.getUsersByIds()`;
    - формирование `editor` через `getFullName()`;
    - отсутствие отдельных запросов для каждой записи.

20. **Fallback при отсутствии пользователя в prm-auth**

    Проверить приоритет:
    - ФИО из `prm-auth`;
    - сохранённое `createdByName`;
    - строковый `createdBy`;
    - пустая строка, если все данные отсутствуют.

    Также проверить нечисловое `createdBy`: оно не должно попадать в запрос пользователей.

21. **Формирование сообщения истории**

    Для `FILE_IMPORT` проверить текст по согласованному шаблону документации с подстановкой `changedObjectsCount`. Использовать несколько значений, например 1, 2, 3. Не придумывать новую формулировку: ориентироваться на текущий контракт проекта.

22. **Проверка параметров запроса**

    Проверить ошибки:
    - `initiativeId <= 0`;
    - `page < 0`;
    - `size = 0`;
    - `size > 100`.

    Проверить допустимые границы `page = 0`, `size = 1` и `size = 100`.

23. **Проверка существования инициативы**

    Несуществующая инициатива → `AiNotFoundException` с корректным кодом. Проверить поведение для отключённой инициативы согласно существующей логике.

24. **Изоляция истории**

    Проверить, что в репозиторий передаётся конкретный `initiativeId`, чтобы история другой инициативы не попадала в результат. Саму корректность JPQL-фильтра не пытаться подтверждать с помощью моков.

### P1 — дополнительные тесты

25. В истории несколько событий одного пользователя: `getUsersByIds()` должен получить один уникальный ID.

26. Проверить, что ошибка получения пользователей, уже обработанная `UserAccountService`, не мешает возвращать историю с fallback-значениями.

27. Проверить корректную передачу стандартных `page = 0`, `size = 20` на уровне контроллера.

## 3. Новое отклонение инициативы AI_OBJECT_REQUIRED

Изучи существующую систему отклонений инициатив, `InitiativeDeviationProperties`, `InitiativeDeviationCode`, стратегии, сервис расчёта отклонений, модели действий и существующий GET отклонений.

**Не создавай отдельную систему отклонений.** Тестируй новую бизнес-логику через существующий механизм.

### P0 — обязательные тесты

28. **Инициатива на стадии MVP без активных AI-объектов**

    Проверить, что формируется отклонение `AI_OBJECT_REQUIRED`.

29. **Инициатива на стадии «Целевое решение» без активных AI-объектов**

    Проверить, что формируется `AI_OBJECT_REQUIRED`.

30. **Инициатива на неприменимой стадии**

    При отсутствии AI-объектов отклонение не должно формироваться. Использовать реальные коды стадий из проекта.

31. **Инициатива с активным AI-объектом**

    Если есть хотя бы один активный объект, отклонение `AI_OBJECT_REQUIRED` не формируется.

32. **Инициатива только с неактивными объектами**

    Если существуют записи, но у всех `isActive = false`, отклонение должно формироваться.

33. **Объект без дополнительных сведений**

    Если существует активный объект с `name = null` и `isAgent = null`, отклонения `AI_OBJECT_REQUIRED` быть не должно. Для этого правила важно наличие активного объекта, а не заполненность его атрибутов.

34. **Отключение правила**

    При `AI_OBJECT_REQUIRED.enabled = false` отклонение не возвращается независимо от стадии и наличия объектов.

35. **Конфигурация отклонения**

    Проверить получение `title`, `description`, `priority`, `cta` из существующего `InitiativeDeviationProperties`, а не из констант сервиса.

36. **Тип действия**

    Проверить, что для `AI_OBJECT_REQUIRED` формируется `OPEN_AI_OBJECTS_TAB`, в соответствии с существующей моделью действий.

37. **Участие в общем расчёте отклонений**

    Проверить, что новое отклонение:
    - попадает в результат существующего GET отклонений;
    - учитывается в общем количестве активных отклонений;
    - корректно участвует в сортировке по приоритету;
    - не нарушает существующие правила расчёта.

### P1 — дополнительные тесты

38. Проверить работу правила для нескольких инициатив с разными стадиями и количеством активных объектов.

39. Проверить отсутствие дублирующегося `AI_OBJECT_REQUIRED` при повторном расчёте отклонений.

40. Если существующий механизм выполняет пакетную проверку отклонений для списка инициатив, проверить отсутствие N+1 вызовов репозитория там, где код предусматривает пакетную обработку.

## Требования к качеству тестов

1. Используй осмысленные имена тестовых методов в стиле проекта.
2. Применяй `@ParameterizedTest` для повторяющихся граничных сценариев, где это упрощает тесты.
3. Избегай излишнего `verify` обычных getter-методов и деталей реализации.
4. Проверяй значения итоговых DTO, исключения и важные взаимодействия с зависимостями.
5. Для проверки отсутствия лишних вызовов репозиториев используй MockK `verify(exactly = 0)`.
6. Все тесты должны быть независимыми, детерминированными и не требовать подключения к внешним системам.
7. Не добавляй интеграционные тесты с БД, Kafka или Feign.
8. Не дублируй уже существующие тесты.
9. Не изменяй бизнес-логику ради прохождения тестов. Если обнаружено расхождение с документацией, отдельно сообщи.
10. После написания запусти новые тесты и исправь обнаруженные ошибки компиляции или тестовых сценариев.
