# Ревью архитектурного плана GigaCode: импорт Excel через staging + atomic apply

**Статус:** план в целом принят как основа, но **не согласован к реализации** до внесения замечаний ниже.  
**Задача GigaCode на следующем шаге:** переработать свой текущий план (разделы 1–12) по замечаниям, проверить спорные решения на реальном коде проекта и вернуть **план v2 без изменения кода, миграций, конфигурации или тестов**. Нельзя начинать «Этап 0» только на основании этого ревью.

## A. Сохранить из исходного плана

1. Обязательную архитектуру **долговременный staging в PostgreSQL → полная валидация → одно атомарное применение бизнес-данных**.
2. Одна транзакция на изменение **всех** затрагиваемых бизнес-таблиц: справочники, блоки/программы/процессы по реальному коду, агенты, метрики, SLA, платформы, ресурсы, контакты, деактивация отсутствующих агентов, QualityGate, refreshStatusesFromAgents; запись `file_upload.SUCCESS` — в том же commit.
3. Раздельные короткие транзакции допускаются **только для технических записей**: регистрации `file_upload`, глобального права на импорт, состояния staging, прогресса, ошибок и cleanup. Никаких изменений бизнес-таблиц в `prepare`.
4. Кандидатные оптимизации: diff метрик и связей, чтение пакетами, отсутствие лишних `save`, кеши `Map`, диагностические измерения, тесты с реальным состоянием БД.
5. **Не считать подтверждёнными** N+1, OOM, утечку JDBC/heap и причину Hikari Thread starvation без измерений.

## B. Обязательные поправки к архитектуре (блокируют реализацию)

### B1. Реальное восстановление после потери исходного Excel

**Проблема:** сейчас исходный файл хранится в `file.bytes` внутри процесса. После рестарта pod байты недоступны. `INSERT ... ON CONFLICT` позволяет продолжать только при наличии повторного источника строк; частичный staging не является полноценным исходным файлом.

**Исправить план:** явно выбрать и документировать одну политику:

- **Предлагаемая базовая политика, если автоматическое возобновление подготовки не требуется:** после рестарта из `PREPARING`/частичного staging маркировать загрузку `ERROR` и запрашивать повторный upload; частичный staging очищать безопасно по политике. **Полностью валидный `PREPARED` можно применять повторно** без исходного Excel (после проверки актуальности и прав на apply).
- **Альтернатива, только если нужен автоматический restart `PREPARING`:** сохранять оригинал в долговременное хранилище с checksum, сроком жизни и безопасным доступом; проектировать идемпотентное возобновление подготовки с проверкой целостности.

Обе политики сохраняют главную бизнес-гарантию: **либо все бизнес-изменения применены, либо ни одно**. Не обещать re-run подготовки с середины файла без сохранённого источника.

### B2. Две разные блокировки: глобальное владение импортом и единственный apply

В исходном проекте `isUploadAllowed()` и `disableUpload()` разделены, что создаёт гонку. Требуется атомарное приобретение `upload_permission` через CAS; владелец — **уникальный `importId`/`ownerToken` UUID**, а не `userId`. Освобождать только владельцу (`WHERE owner_token = :token`), иначе поздний `finally` старой задачи может разблокировать новую.

**Недостаток предложенного CAS на staging:** `PREPARED -> APPLYING` по `fileUploadId` предотвращает двойной apply **того же файла**, но не сериализует **два разных** `fileUploadId`. После истечения TTL lease живой старый pod может продолжать работу, пока второй импорт уже получил lease.

**Исправить:** помимо CAS статуса одного импорта в одной apply-транзакции использовать транзакционный механизм, гарантирующий **не более одного активного apply во всём кластере** (например, PostgreSQL `pg_advisory_xact_lock` с единым ключом для всех импортов, либо эквивалентную документированную блокировку строки). После получения mutex заново проверять владельца/актуальность lease и состояние импорта; при утрате права прекращать apply без записи бизнес-данных. Описать порядок захвата блокировок и таймауты.

**TTL сам по себе не доказывает, что старый поток прекратился.** Нужны heartbeat/recovery/стратегия fencing и тест «старый pod жив, lease истёк, второй pod начал импорт». Особое внимание: отдельный heartbeat, обновляющий строку, заблокированную долгой apply-транзакцией, может ждать до commit; избегать самоблокировки при проектировании.

`isUploadAllowed()` сейчас ловит **любую** ошибку БД и возвращает `true`. Заменить fail-open на строгое различение «запись не существует» и реальной ошибки БД; миграцией инициализировать `GLOBAL`. При недоступной БД импорт не разрешать.

### B3. Durable dispatch после регистрации

`CompletableFuture.runAsync()` из `@Transactional upload()` сейчас стартует раньше commit, а `saveAndFlush()` не гарантирует видимость новой записи другому соединению.

Исправление: регистрация и CAS блокировки — короткая транзакция; запуск воркера **после commit**. Однако простой `afterCommit` не закрывает окно «регистрация закоммичена, процесс умер до постановки задачи».

Предложить **надёжный механизм постановки/подхвата задачи из БД** (например, техническая очередь/outbox или lifecycle-поллер по состоянию регистрации), достаточный для выбранной политики B1. Для `PREPARED` recovery обязан уметь повторно подхватить задачу. При отказе bounded executor/rejected submission состояние не должно вечно оставаться `PROCESSING` с занятым lock.

### B4. Статусы и crash-consistency на границе commit

Сохранить публичные `file_upload.status = processing|success|error`. Фазы staging — отдельная техническая машина состояний (`REGISTERED`, `PREPARING`, `PREPARED`, `APPLIED`, `FAILED`; `APPLYING` может существовать только внутри незавершённой транзакции).

Требуемые инварианты:

1. `file_upload.SUCCESS` и все бизнес-изменения фиксируются **одним commit**. Никакого дополнительного `REQUIRES_NEW updateStatus(SUCCESS)` после commit.
2. Если prepare завершился ошибкой: бизнес-данные не изменены; `ERROR` пишется отдельной короткой транзакцией.
3. Если apply откатился: техстатус `ERROR` пишется **после rollback**, в отдельной транзакции. Внутри откатываемой apply-транзакции `ERROR` не сохранится.
4. Если процесс погиб или JDBC-клиент потерял ответ **после успешного commit**, recovery обязан сначала проверить зафиксированные маркеры в БД и не применять импорт повторно/не помечать успешный импорт ошибочным.
5. Захват `PREPARED -> APPLYING` и переход `APPLIED` делаются так, чтобы после rollback не остался ложный «применён»; по commit атомарно становятся видимыми `APPLIED` + `SUCCESS`.
6. Освобождение глобального права и cleanup выполняются после commit как **идемпотентные технические операции** с проверкой ownerToken. Их неуспех не отменяет уже состоявшийся бизнес-commit; recovery завершит их позднее.

В плане явно указать таблицу состояний: до/во время/после prepare и apply, commit/rollback, возможный crash, повторный запуск, видимость `file_upload`.

### B5. Актуальность данных между prepare и apply

`staging` не замораживает боевые таблицы. Jira/PULT/шедулеры могут изменить агента/связи после подготовки и до apply, а также во время apply.

В v2 описать, **какие сведения** в staging являются сырьём из Excel, какие — ссылками на бизнес-данные, и **когда** выполняется разрешение FK/бизнес-ключей. Нельзя слепо применять устаревший снимок.

Проверить `@Version`, `updated`, реальные SQL updates, блокировки на уровне БД, логику приоритетов PULT/Jira/Excel и доступные варианты `optimistic locking`, `SELECT FOR UPDATE`, перепроверки preconditions внутри apply. Определить политику конфликта **abort с `ERROR` / пересчёт / ограниченный retry**; никакой тихой перезаписи более новых данных.

**Snapshot token не обеспечивает согласованность сам по себе**, если не связан с механизмом обнаружения изменений. Не придумывать общий timestamp/version для всех таблиц без анализа.

### B6. Атомарность vs длительная транзакция и производительность

Staging переносит парсинг и часть проверок за пределы основной транзакции, но **одна apply-транзакция остаётся длинной**. Это требование бизнеса; простой переход на staging не гарантирует исчезновения `Thread starvation`, ожиданий блокировок или рестартов pod.

Добавить анализ возможностей `JDBC/Hibernate batching`, размеров пачек, `flush/clear`, `@Version`, стратегии генерации ID, долгих native UPDATE, порядка SQL и конкуренции с Jira/PULT. Следить, чтобы не появились detached-сущности в managed коллекциях. **Не делить бизнес-apply на промежуточные commit**. Для честного сравнения измерять отдельно parse, staging-write, подготовку diff, время ожидания mutex, SQL apply, flush, commit и cleanup; количество операций и RSS/heap/GC.

### B7. Нельзя самовольно менять семантику «неизменившегося импорта»

Изменение «идентичный файл → ни одного UPDATE» **не является текущим контрактом**: `agent.updated` меняется при каждом импорте и влияет на Jira/PULT. `involvedResource.updated`, `plannedDate`, `completedDate`, `released`, статус и история могут иметь потребителей.

- До согласования сохранять нынешнюю семантику временных полей, даже если часть UPDATE останется.
- `AppliedMetricRepository.deleteAllByAiAgentId()` затрагивает текущий набор типов; **не исключать пользовательские метрики автоматически**. Сначала восстановить точную политику по исходному запросу, связи типа/ключа и тестам; diff должен давать то же итоговое состояние БД, что прежняя полная пересборка, пока бизнес не согласует изменение.
- Глобальное `deleteAllForImportedNonBlockedAgents()` может очищать контакты агентов, **отсутствующих в Excel**. Покомпонентный diff по загруженным агентам без финальной очистки будет регрессией. Сохранять эквивалентный эффект (с учётом PULT/blocked) **внутри общего apply**.
- Проверить точные `cascade`, `orphanRemoval`, composite keys, owning/inverse sides. `entityManager.clear()` + загрузка дочерних сущностей отдельным репозиторием требует аккуратной работы с managed состоянием, а не механической подмены коллекций.
- N+1 на `platforms/involvedResource` пока гипотеза; оптимизацию batch fetch обосновать статистикой SQL.

### B8. Подготовка staging должна быть полной и детерминированной

До `PREPARED` все обязательные листы, колонки, типы, номера строк/столбцов, формулы/кэшированные значения, дубли agentId, справочные коды, метрики, принадлежность агентов импорту и остальные валидации должны быть представлены в staging или гарантированно проверены.

- Нормализованная структура предпочтительна для бизнес-ключей, индексов и batch diff; JSON допускается как **дополнение** для оригинальных значений/диагностики, а не единственная модель.
- Уникальные ограничения по `file_upload_id + тип сущности + бизнес-ключ` и FK не должны терять допустимые дубли и ошибочные строки **до того, как формируется прежнее корректное сообщение об ошибке**. Сначала выявить допустимые и недопустимые дубли согласно старой логике.
- Маркер `PREPARED` ставить только после проверки полноты staged набора, отсутствия ошибок и успешного commit всех staging-пачек. Не применять половину файла.
- Описать объём staging, индексы, retention, cleanup ошибочных/успешных записей, защиту от случайной очистки активного импорта, checksum/размер (если исходный файл сохраняется), отсутствие staging в обычных GET/export.

### B9. Внешние побочные эффекты и rolling deploy

Проверить фактические HTTP вызовы из QualityGate, Jira/PULT, listeners, аудита. Их **нельзя откатить PostgreSQL rollback**; при наличии запись намерений в outbox внутри apply и отправка после commit с идемпотентностью.

Предложенное «старый и новый путь одновременно под одним CAS» требует проверки: **старые версии приложения не знают ownerToken, heartbeat, новые поля и правила освобождения**. Одна только обратная совместимость таблиц не делает rolling deploy безопасным.

Нужен явный rollout-план: preflight/миграции, остановка/дренирование старых активных импортов либо подтверждённое совместимое переключение, единый механизм блокировки для обеих версий, recovery старых `PROCESSING`, feature flag только при безопасном состоянии. Rollback приложения допустим только с обеспечением безопасности незавершённых imports. **Не выполнять автоматически DROP staging-таблиц при rollback**, если там остались необходимые для recovery данные.

### Бизнес-данные и диффы

### Сбои, конкурентность и миграции

- Rolling deploy old/new и rollback версии с незавершённым `PROCESSING`.
- Базовые измерения по идентичному **валидному** файлу: 5–6 **последовательных** загрузок с ожиданием окончательного `success/error`; heap/RSS/GC, Hikari, SQL counts, lock waits, длительность apply/commit. Не смешивать с параллельным стресс-тестом.

## F. Бизнес-решения, которые нельзя принять по одному коду

- Нужно ли именно **автоматически продолжать `PREPARING`** после рестарта или допустимо `ERROR` и повторная загрузка файла? (Рекомендация: базово второй вариант; `PREPARED` восстановим автоматически.)
- Какой допустимый срок хранения staging после `SUCCESS` и `ERROR`? Есть ли требования к хранению исходного Excel?
- Разрешено ли менять семантику `agent.updated`, `involvedResource.updated`, SLA дат и правила удаления метрик? (До решения — не менять.)
- Нужно ли гарантировать немедленное отклонение нового импорта при активной загрузке или возможна очередь? (Сохранить текущий ответ/контракт, если не согласовано иначе.)
