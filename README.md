# Финальное ревью плана GigaCode v2: корректировки до начала реализации

**Вердикт:** направление `staging PostgreSQL → полная проверка → единая транзакция apply` и этапы 0–6 **согласованы как план работ**. **Полный запуск реализации пока не согласован:** сначала в Этапе 0 надо закрыть нижеперечисленные архитектурные условия. Не переписывать весь план заново, внести точечные поправки и согласовать короткий технический дизайн Этапа 0. До этого код не менять.

## 1. Блокирующее противоречие: `REGISTERED` невозможно восстановить без исходного Excel

В B1 выбрана политика **не хранить исходный Excel**, поэтому после рестарта `PREPARING`/частичный staging → `ERROR` и повторная загрузка пользователем. Но в B3 предлагается «`REGISTERED`, не взятый в работу через N времени → подхватывается поллером». Если pod потерял файл ещё до начала подготовки, поллеру нечего читать: `file.bytes` были только в памяти.

**Исправление:** для `REGISTERED` и `PREPARING` после потери процесса/байтов выбирать **`ERROR`, release права владельца и очистку частичного staging по политике**. Поллер может восстанавливать **только полностью завершённый, валидный `PREPARED`**, который не требует исходного файла. Повторно исполнять `REGISTERED` допустимо лишь при наличии **надёжно сохранённого оригинала** с checksum/доступом (отдельная, не выбранная сейчас архитектура). Статус «работник был жив» выяснять по lease/heartbeat, чтобы не признать живую задачу ошибочной. Нельзя одновременно обещать durable-dispatch `REGISTERED` и не сохранять источник.

**Тест:** процесс падает после регистрации и commit, но до `afterCommit`/первого чтения файла; после рестарта загрузка получает `ERROR`, не висит в `processing`, право на импорт освобождено; бизнес-таблицы неизменны. Отдельно: crash после `PREPARED` восстанавливает apply без Excel.

## 2. Lease/fencing проверять не только при входе в `apply`, но и непосредственно перед COMMIT

В B2 корректно предложен единый `pg_advisory_xact_lock` для сериализации разных импортов и `ownerToken`. Но **advisory lock исключает одновременный apply, а не гарантирует сохранение владельца глобального lease до commit**. Длинный apply может длиться дольше TTL: новый pod получит lease, а старый всё ещё держит advisory lock и затем успешно закоммитит, хотя право уже утрачено.

**Исправление:** в одной apply-транзакции после получения advisory lock проверять текущего владельца/валидность lease и статус импорта, **а перед commit делать транзакционную финальную проверку/fencing владения**, например условный `UPDATE upload_permission ... WHERE id='GLOBAL' AND owner_token=:token AND lease_expires_at > now()` с проверкой числа обновлённых строк. При утрате права — исключение и rollback **всех бизнес-изменений**. Уточнить блокировки строки, гонку с выдачей нового lease, поведение heartbeat и lock order; не удерживать lock той же строки на весь apply, если heartbeat обновляет её в отдельной транзакции. Освобождение права — только по ownerToken.

**Тест:** старый worker жив и продолжает длинный apply, lease истёк, второй worker получил право. Первый **не должен** зафиксировать устаревший apply после утраты права; второму нельзя одновременно изменять бизнес-таблицы. Подтвердить отсутствие deadlock с heartbeat.

## 3. `agent.updated` сам по себе недостаточен как универсальная защита от потери изменений Jira/PULT

В B5 предлагается сравнивать `agent.updated` «с момента подготовки» с текущим значением и `abort`. Это можно использовать **только если** сохранён исходный marker каждого затронутого агента и проверено, что **каждый конкурентный изменяющий путь** действительно обновляет этот marker. В проекте отсутствует `@Version`, встречаются bulk SQL, глобальные очистки, deactivation и обновление дочерних таблиц. По одному `agent.updated` нельзя надёжно выявить все конфликты.

**Исправление:** в Этапе 0 составить карту записей из Excel/Jira/PULT/шедулеров/ручных действий **по таблицам**, включая связи, отсутствующих в файле агентов и справочники; определить набор затрагиваемых ключей, правила обновления маркеров и lock order. Для каждой конфликтующей операции указать действительный DB-механизм проверки **внутри apply**, после необходимых блокировок и до записи. Не полагаться на таймштамп без доказанной полноты; рассмотреть версионирование/предикатные SQL-проверки/блокировки там, где нужно. `READ COMMITTED` сам по себе не обеспечивает сохранение старого снимка для серии запросов.

**Отдельно:** восстановление старого `PREPARED` после того, как другая более новая загрузка уже успела примениться, не должно молча перезаписывать её. Задать политику порядка импортов/конфликта: базово безопасно **abort с `ERROR`** и повторная загрузка.

**Тест:** Jira меняет того же агента после staging, до apply; параллельно меняется связь/контакт без обновления `agent.updated`; появляется ранее отсутствовавший agentId; изменяется запись из глобальной очистки. Нет тихой потери более новых данных.

## 4. Строго проверить транзакционные границы зависимых сервисов

`SUCCESS` в `file_upload` и все изменения реестра должны войти в **один реальный commit**, а не только исполняться «внутри `AiaImportApplyService`» по названию. На Этапе 0 проверить фактические Spring-аннотации, `REQUIRES_NEW`, self-invocation, native bulk операции, event listeners, QualityGate и вызовы `refreshStatusesFromAgents`. Любой вызов, который пишет бизнес-таблицы в собственной транзакции или выполняет HTTP/событие до commit, нарушит целевую атомарность.

**Тесты:** искусственная ошибка непосредственно после записи словарей, после QualityGate и перед commit: **никаких** изменений ни в одной бизнес-таблице; `ERROR` записывается после rollback отдельной технической транзакцией. После успешного commit последующая ошибка cleanup не должна переводить `SUCCESS` в `ERROR`.

## 5. Неблокирующие уточнения к Этапу 0

- **N+1:** статический анализ `LAZY` inverse-коллекций подтверждает риск отдельного SELECT на каждого агента; реальное количество запросов и выигрыш всё равно измерить.
- **Метрики:** текущий import удаляет **все типы** и создаёт `STANDARD`. Diff обязан сохранить итоговый эффект до изменения бизнес-контракта; у идентичных бизнес-значений может измениться identity/ID/дата, если они кем-то используются — проверить, какая эквивалентность нужна.
- **Время `updated`:** пока менять нельзя. Это может ограничить ускорение повторного импорта; отделить необходимые бизнес-UPDATE от устранимых DELETE/INSERT.
- **Hibernate batching:** проверить фактическую стратегию генерации PK, совместимость `hibernate.jdbc.batch_size` и количество выполняемых SQL; топ-уровневый `BATCH_SIZE` не включает JDBC-batching автоматически.
- **Staging integrity:** `PREPARED` только после коммита **всех** пачек и проверки их полноты. Уникальные ключи не должны «съедать» дубли и ломать сообщения валидации по Excel-строкам.
- **Retention:** сроки хранения staging после `SUCCESS/ERROR` установить параметризуемыми, а cleanup не должен удалять `PREPARED`/живой импорт. Точные дни согласовать позднее.
- **Rollout:** старые pod не умеют работать с `ownerToken`: необходим дренаж активных старых импортов или доказанная совместимость; одного feature flag недостаточно.

## 6. Решения по бизнес-поведению, предлагаемые к согласованию

1. **Выбранная политика crash до `PREPARED`:** `ERROR` + повторная ручная загрузка; `PREPARED` — восстановление без Excel.
2. **При активном импорте:** сохранять существующий контракт отказа (`403 file.upload.is.not.allowed`), очередь без отдельного требования не вводить.
3. **При конфликте с Jira/PULT:** прекращать применение/rollback и фиксировать `ERROR`, без тихой перезаписи (точные критерии конфликта подтвердить картой записей).
4. **`agent.updated`, SLA даты, типы метрик, контакты отсутствующих агентов:** сохранить действующее поведение до отдельного бизнес-согласования.
5. **Retention staging:** срок вынести в конфигурацию; согласовать значение с эксплуатацией, не придумывать фиксированный TTL в миграции.
